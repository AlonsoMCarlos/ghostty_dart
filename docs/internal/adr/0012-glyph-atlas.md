# 0012. Glyph atlas for grid text (`drawRawAtlas`)

**Status:** Accepted (2026-11-10). Proposed the same day after a spike; production design and measurements of wave B below. Plan run: `.claude/plan-runs/20261110-glyph-atlas/` (research `investigacion/A-research.md`, spike `resultados/A.md`, production `resultados/B.md`). Amends ADR 0011 "Rendering (v1)" and its 2026-11-10 "render performance" amendment.

## Context
- After ADR 0011's render-performance amendment the widget won idle, scroll, 3 dirty rows and cache replay against xterm 4.0.0, but lost whenever rows held *new* text: a full 200 × 60 screen of new styled text cost 32.30 ms write + UI (xterm 4.0.0: 21.58) and the htop-like screen 33.32 (19.63) on the benchmark VM (DPR 2, Impeller on llvmpipe, `benchmarks/README.md`). 3 dirty rows cost 2.49 ms against the 1 ms target.
- Probes of the fresh frame: ~28 ms of the ~31 ms spent in `RenderTerminal._pullFrame` was recording rows, almost all of it `ui.Paragraph` build + layout (one paragraph per row, ~0.45 ms per 200-column row). The paragraph API cannot get cheaper per row, and caching rows does not help content that is new.
- xterm 4.0.0 avoids layout by caching one paragraph per (character, colours, flags) and calling `drawParagraph` per cell. A glyph atlas does the same with less per-cell work: one `drawRawAtlas` per row with one transform, source rect and colour per glyph, no layout.
- `Canvas.drawRawAtlas` exists on every renderer we target (Impeller, Skia, CanvasKit, skwasm; sources in the research note). No open issue blocks our use (sprites on whole device pixels, no colour filter, at most one row of sprites per call).
- Text rasterisers adjust glyph coverage to the text colour's luminance: Impeller on Linux and Windows raises coverage to `1 + 1.2·luma` in its glyph shader (`impeller/entity/contents/text_contents.cc`, `shaders/glyph_atlas.frag`), Skia does the same with its mask gamma. A white glyph tinted afterwards therefore draws dark and coloured text heavier than a paragraph would (spike: mean |Δ| 7.1 per differing channel on Impeller).

## Decision

**Public option.** `VtTerminalView.textRendering` takes `VtTextRendering.atlas` (default) or `VtTextRendering.paragraphs` (ADR 0011's row paragraphs). The paragraph path stays: as the opt-out (exact paragraph shaping, contextual forms, exact per-colour coverage, views shown under a scale transform, debugging), as the fallback for glyphs the atlas does not hold, and as the reference of the differential tests. Changing the option drops the caches like a font change.

**What goes in the atlas.** Every cell of a style run that `RowRecorder` already treats as grid-safe (narrow, single BMP code unit, `isGridSafe`, not a space), in all four faces (regular, bold, italic, bold italic). The rest keeps the paragraph path unchanged: wide characters, grapheme clusters, emoji and other non-grid-safe text (`_opCluster`), box drawing (stretched clusters), the block cursor's glyph, and any grid-safe code unit whose single-glyph advance is not one cell within half a device pixel (a glyph from a fallback font), drawn by `_drawCluster` after the row's atlas calls.

**Key.** `(code unit, faces, luminance bucket)` packed as `bucket << 18 | faces << 16 | unit`: at most 22 bits, so it is exact on the VM, on wasm and on dart2js (whose integers are doubles and whose bitwise operators work on 32 bits). Printable ASCII has a flat `Int32List` lookup (16 buckets × 4 faces × 128); everything else a map. The engine-style cache of `RowRecorder` keys by `color * 8 + faces` (arithmetic, 35 bits) for the same reason.

**Colour: luminance buckets only.** A glyph is rasterised in a grey whose luminance is the cell colour's (Rec. 709 luma, quantised to 16 levels) and drawn with `BlendMode.dstIn` and the cell colour in `colors`, so only its alpha is used. A cell colour that is exactly its bucket's grey (the default theme's foreground `#cccccc`, white, black) needs no tint: those sprites go into a second `drawRawAtlas` call of the row without `colors`, which Impeller draws with its plain texture pipeline instead of the per-sprite blend (17 % less raster time on the benchmark, see Evidence). Each bucket gets the rasteriser's own coverage for that luminance; the key space is at most 16 × glyphs × 4 faces whatever colours a program uses, and the theme's palette does not enter the key (a theme or palette change keeps the atlas). The theme's default foreground (`#cccccc` → bucket 12, grey 204) is reproduced exactly. The spike's other modes are **dropped**: white glyphs tinted with `modulate` (visibly heavier dark and coloured text) and colour-keyed glyphs (rasterised in the exact cell colour, xterm's key space). Colour-keyed matched paragraphs to ±1 and avoided the per-sprite blend on the raster thread, but its key space grows with every truecolor value (`lolcat` fills any budget) and needs the full ARGB in the key; no renderer was found where luminance is not the only colour input of glyph coverage, so it is not kept even as an option.

**Geometry.** Slots are whole device pixels: one cell plus a margin of half a cell left and right, 3/10 of a cell above and 1/8 below. Measured with the pinned JetBrains Mono over every grid-safe glyph in all four faces (DPR 1–3, 12–20 px): ink leaves the cell by up to ~0.3 cell width on either side (Greek tonos `Ύ`, italic `Ĵ`), up to 0.25 cell height above (`Ǻ`; the spike's quarter-cell top margin was borderline at 12 px, DPR 1) and never below. `glyph_atlas_test.dart` asserts that no glyph touches its slot's border, so a font change that clips is caught. A glyph is rasterised from a one-character paragraph in the grid style (same letter spacing, ligatures and `calt` off) at the same sub-pixel offset inside its slot that it has inside its cell, under `scale(devicePixelRatio)`, and drawn back with `RSTransform(scos: 1/dpr, tx: col·width − margin)` and nearest sampling: one texel per device pixel. Bilinear sampling (`FilterQuality.low`) gives the same pixels at 1:1 and blurs instead of aliasing under a scale transform, but cost ~4 % more raster time; paragraphs are re-rasterised at the final scale anyway, so a view shown scaled is the case for the paragraph path, not for a softer atlas.

**Pages and flushes.** Slots live in fixed-size pages: at most 1024 × 512 device pixels and at most ⅛ of the view's cache budget (2 MiB by default), at least one slot. `slotOf` gives a new glyph the next free slot and queues it; `flush` rasterises every queued glyph at once with `Picture.toImageSync`, one new image per page that got glyphs (the page's previous image copied in first). A full page never changes again. The renderer:
- prefills printable ASCII (U+0021–007E) in the regular face and the default foreground's bucket into page 0 when a frame first needs it (once per bucket), and flushes;
- records the frame's changed rows; a row that needs a glyph that is only queued is not kept (`RowRecorder.missedGlyphs`);
- flushes once, after all rows, and records only the missed rows again.
So a page gets at most one new image per frame (the spike made one per row with misses, each a copy of the whole atlas), and at steady state there is no extra cost. The alternative, reserving each row's glyphs in a pre-pass before recording, would cost a second lookup per glyph on every frame; re-recording a missed row costs only on frames with new glyphs.

**Calls.** One `drawRawAtlas` per row, page used and tint (tinted / untinted), inside the row's cached picture, after the row's backgrounds and before clusters and decorations (ADR 0011's stacking). No `cullRect`: passing the sprites' bounds changed nothing measurable. Never one call per frame: row pictures stay content-keyed and cacheable, and skwasm's per-call sprite limit (#185995) stays irrelevant.

**Memory.** A recorded picture holds its own reference to the page image it draws, so a replaced page image stays alive while cached pictures use it. `AtlasImage` does the accounting: every cached row picture retains the page images it draws and releases them when it is disposed; a replaced image is retired and freed with its last user. `AtlasLedger` sums the bytes (4 per pixel) of every image not freed yet, live or pinned, across atlas generations of a view.
- **Budget.** `cacheBudget` (16 MiB by default) is now pictures + atlas images ≤ ¾ and paragraphs ≤ ¼. Eviction disposes the least recently used pictures not shown in the current frame until pictures plus the ledger fit; each eviction releases the images it pinned, so the ledger shrinks as it goes.
- **Atlas cap.** When the atlas's live pages exceed ½ of the budget and twice what they held after the generation's first frame, the next paint drops the atlas and every picture and records the screen into a new atlas. The "twice the first frame" floor keeps a screen that alone needs more than the cap from rebuilding every frame.
- **Release.** The atlas belongs to the `RowRecorder`, so everything that already drops the recorder drops it: font, size, DPR, text scaler and metrics changes, a `textRendering` change, system font changes, detach, 5 s hidden, dispose. On memory pressure the renderer keeps the visible rows as before, and drops the atlas with every picture (recording the screen again on the next frame) only if the atlas has a page that no visible row draws.

**Web.** Same path on CanvasKit and skwasm once `ghostty_dart` has its wasm backend; the key is already web-safe. Until then the package stays native-only.

## Consequences
- A screen of new text no longer lays out paragraphs. On the benchmark VM (numbers below) write + UI drops from ~33–35 ms to ~6.2–6.5 ms for a fresh full screen and the htop-like screen, about 3.3× faster than xterm 4.0.0, and 3 dirty rows from 2.5 ms to 0.92 ms (xterm 4.0.0: 19.3).
- **Raster thread on a software rasteriser: slower.** On Mesa llvmpipe the atlas costs ~1.2–1.3× the paragraph path's raster time (122–127 ms against 98–104; xterm 4.0.0: 155–160, see Evidence). It is per-sprite work, not fill (sprites shrunk to the bare cell did not change it), and it does not change with a `cullRect` or the paint's anti-aliasing; drawing exact-grey sprites untinted and nearest sampling are kept because they cut it (see Evidence). **Open question:** whether a real GPU shows the same ratio. Impeller draws the atlas with its Porter-Duff blend pipeline (`AtlasContents`), one textured quad per glyph; on a GPU that is normally cheap, but it is unmeasured. The paragraph path is one opt-out away if it matters on some device. Measure `mise run bench:widget` on a machine with a GPU before claiming anything about raster time.
- Text is drawn glyph by glyph without shaping context. Fonts whose default shaping changes a glyph by context even with `liga`/`calt` off draw the isolated form instead (seen on Impeller: JetBrains Mono's grave accent after a letter, 3 cells of a 1,920-cell screen). Ligature-free grid text is what a terminal wants; this is accepted and documented on `VtTextRendering`.
- Coverage is the platform rasteriser's for the nearest of 16 luminance levels, not the exact colour: on flutter_tester (Skia) 0.4–0.7 % of the pixels of a mixed screen differ from paragraphs by more than premultiplied rounding (±1), by at most 12 of 255 (asserted in `test/render/glyph_atlas_test.dart`); the default foreground is exact.
- A view shown under a scale transform resamples its atlas glyphs (nearest); paragraphs would be re-rasterised. Goldens captured at 1× of a DPR-2 scene show it (deltas up to 174 on glyph edges). Documented on `VtTextRendering.paragraphs`.
- **Cache replay is slower than with paragraphs on the benchmark's synthetic streams.** Their random 16/256/truecolor words in four faces use ~13 luminance buckets, 1,222 slots, 4 pages (7.8 MiB at DPR 2), which leaves the 480-row replay cycle (8 screens × 60 rows) less than the ¾ share it needs, so part of it is recorded again each frame (still about 3.5× faster than xterm 4.0.0, see Evidence). Atlas-row pictures are estimated by what their display list stores (`RowContent.estimatedAtlasBytes`, ~64 bytes per glyph instead of the paragraph path's 96), so the budget is not overcharged; the budget stays 16 MiB (it is not a `VtTerminalView` parameter yet; exposing it is a follow-up), and an app that replays many heavily styled screens can use paragraphs. A shell session uses one or two pages.
- More GPU memory per view (a few MiB of atlas pages, counted in the budget) and a second text path to keep correct; the differential tests (atlas against paragraphs, warm caches against a cold renderer on both paths) and goldens of both paths guard it.

## Evidence
All on the benchmark VM (AMD Ryzen 5 3600, 6 vCPUs, no GPU; Xvfb 3840 × 2400, Mesa llvmpipe; Flutter 3.47.9, Impeller OpenGL ES; DPR 2; 200 × 60 cells, JetBrains Mono 12 px; profile mode).

**Full benchmark** (`GDK_SCALE=2 xvfb-run -a -s '-screen 0 3840x2400x24' mise run bench:widget`, final code, 2026-11-10, 3 passes × 300 frames, 900/900 frames in every run; table in `benchmarks/README.md`). Write + UI average / raster average, ms:

|---|---|---|---|---|
| idle | 0.14 / 122.2 | 0.15 / 103.4 | 0.16 / 155.2 | 0.15 / 137.7 |
| 3 dirty rows | 0.92 / 126.1 | 2.49 / 97.7 | 19.31 / 157.0 | 24.83 / 146.5 |
| full screen, fresh | 6.52 / 125.4 | 32.70 / 98.3 | 21.84 / 159.9 | 26.88 / 148.0 |
| scroll (cat) | 1.23 / 106.2 | 1.90 / 103.3 | 6.02 / 77.5 | 6.91 / 82.4 |

| full screen, warm (cache replay) | 5.94 / 127.0 | 3.27 / 99.6 | 20.85 / 157.7 | 25.54 / 146.4 |

An earlier full run the same day (before the asymmetric margins and the atlas picture estimate) gave the same picture: atlas fresh 5.50, htop 5.40, 3 rows 0.88, replay 5.62 (paragraphs 2.81), raster 107–129 ms.

**Raster mitigations** (temporary probe on the same streams, `FrameTiming`, 150 frames after 32 warm-up, same run, ms of raster time; UI unchanged within noise):
- probe 1 (one pass): bilinear sampling with `cullRect` 158.3 / 159.2 / 151.9 / 151.3 (fresh / htop / idle / 3 rows); without `cullRect` 159.0 / 158.4 / 151.4 / 150.2 (no effect: dropped); `isAntiAlias = false` 160.1 / 158.9 / 150.9 / 150.4 (no effect); nearest sampling 153.9 / 151.5 / 146.8 / 145.1 (−4 %: kept); paragraphs 95.7 / 108.6 / 102.7 / 102.6.
- probe 2 (two passes for fresh and htop): atlas 159.5 and 152.6 / 159.6 and 161.1; exact-grey sprites untinted 132.3 and 132.1 / 132.8 and 134.2 (−17 %: kept); untinted + nearest 126.9 and 125.8 / 126.4 and 126.1; idle 151.7 → 130.2 → 125.0; paragraphs 94.1–98.5.
- The spike's margin experiment (sprites shrunk to the cell: unchanged) still says per-sprite, not per-pixel, cost.

**Pixels.** `test:grid-pixels` on Impeller (`xvfb-run -a mise run test:grid-pixels`): 24 of 24 cases (4 DPRs × 3 sizes × both paths) 0 px off the grid, 0 px drift at column 199. flutter_tester (Skia), 40 × 8 mixed screens with truecolor, 8 screens: pixels differing from paragraphs by more than 1: 0.73 % (DPR 1), 0.58 % (1.5), 0.44 % (2), max |Δ| 12. Goldens: the paragraph golden of the 200 × 60 screen is identical to the old one; the atlas goldens at 1:1 differ by rounding (mixed screen 3.7 % of pixels, max 18, mean 1.1; screenshot 0.9 %, max 19); goldens captured at 1× from a DPR-2 scene differ on glyph edges by up to 174 (nearest resampling), invisible at a glance.

**Atlas size.** Bench streams at DPR 2: 1,222 slots, 4 pages of 396 slots (1.99 MiB each), steady from the setup screen on; the replay cycle then keeps ~310 of 480 row pictures.

**Spike numbers** (wave A, `resultados/A.md`): fresh 32.5 → 5.2 ms, htop 34.2 → 4.7, 3 rows 2.5 → 0.80 write + UI; recording a fresh frame 27.6 → 1.7 ms (`_pullFrame` probes).
