# 0014. Kitty graphics images in `ghostty_dart_flutter`

**Status:** Accepted (2026-11-13). Extends ADR 0011 (widget architecture) and ADR 0012 (glyph atlas, cache budget); both stay in force.

## Context
- libghostty-vt 1.0 implements the [Kitty graphics protocol](https://sw.kovidgoyal.net/kitty/graphics-protocol/) (`kitty_graphics.h`, render-state image iterator), and our prebuilt binaries are built with it (`VtFeature.kittyGraphics`). Its storage is **on by default** with a 10 MB limit per screen (`GHOSTTY_TERMINAL_OPT_KITTY_IMAGE_STORAGE_LIMIT`, `terminal.h`), and it answers the protocol's `a=q` support query.
- `ghostty_dart` 0.1.x already exposes everything a renderer needs: `RenderState.imagePlacements()` / `imagePlacementsGeneration` (viewport-relative placements with layer, z, source and destination rectangles in device pixels, image generation), `VtTerminal.kittyImagePixels()` / `kittyImage()`, `tickKittyAnimations()`, and the process-wide synchronous PNG hook `setVtPngDecoder`.
- `VtTerminalView` draws none of it. Programs such as `kitten icat` therefore believe the terminal supports images (the query is answered), transmit them, and nothing appears. Found while dogfooding vtterm (2026-11-13).
- PNG is the default transmission format of `kitten icat` (`f=100`). The library decodes it through `setVtPngDecoder`, **synchronously inside `vt_write`**, so Flutter's asynchronous codecs (`instantiateImageCodec`) cannot serve as the decoder.

## Decision

**Drawing.** The render box draws the render state's placements on every paint, re-reading the list only when `imagePlacementsGeneration` changes (it changes when placements move, too). Placements with `ImageProtocol.unknown` are skipped. Each one is drawn from its source rectangle (`sourceX/Y/Width/Height`, image pixels) into the destination `(viewportCol * cellWidthPx + cellOffsetX, viewportRow * cellHeightPx + cellOffsetY, pixelWidth, pixelHeight)` in device pixels, divided by the device pixel ratio, clipped to the grid. Order: by layer, then `z`, then iterator order. `belowBackground` and `belowText` are drawn after the default background and before the row pictures; `aboveText` (and `unknown`, as `ghostty_dart` advises) after the rows, before the cursor and the highlights (so search highlights stay visible over an image). Row pictures paint cell backgrounds and text together, so a `belowText` image sits under non-default cell backgrounds instead of above them; Kitty's own split would need a separate background pass per row, which is not worth its cost for a z-range programs rarely combine with coloured cells. Documented as a known difference.

**Textures.** One `ui.Image` per `(imageId, imageGeneration)`, created with `decodeImageFromPixels` from `kittyImagePixels` (RGB, grey and grey+alpha are expanded to RGBA in Dart first). Creation is asynchronous: the placement appears on the frame after its texture is ready, and the box repaints then. Textures of images no longer placed are disposed at the next placement re-read; stale generations are disposed when their replacement is ready (so an animation never flashes empty). Textures are not counted in `cacheBudget`: that budget bounds caches that can be dropped and rebuilt, while a placed image must be shown; their memory is bounded by the terminal's storage limit, which apps set with `VtTerminalController(imageStorageLimit:)` (null keeps the library's 10 MB per screen, 0 disables the protocol entirely; a constructor parameter so it applies before the first byte, `controller.terminal.kittyImageStorageLimit` still works later).

**Animations.** The controller calls `tickKittyAnimations` on a monotonic `Stopwatch` clock started with the controller, whenever the storage generation shows images and after each tick, and schedules a single `Timer` for the returned due time; a tick that changes frames notifies listeners like output does. No timer runs while nothing animates.

**PNG.** `ghostty_dart_flutter` ships `decodeVtPng`, a small synchronous PNG decoder in pure Dart over `dart:io`'s zlib (the package is native-only, ADR 0011): every colour type and bit depth, palettes with `tRNS`, Adam7 interlacing; no colour management (gamma, ICC and `sRGB` chunks are ignored, as in most terminals). It runs on untrusted input, so it is fail-closed: CRCs checked, chunk order enforced, dimensions bounded (≤ 16384 per side and ≤ 64 MiB of RGBA), the inflated size checked against the exact size IHDR implies while inflating (no decompression bombs), and any error returns `null` (image rejected). A dependency was rejected: `package:image` would pull `archive` and `xml` into every app for one format, and the decoder is ~300 lines with fuzz tests. Installing it stays explicit (`setVtPngDecoder(decodeVtPng)` once at start-up): the hook is process-wide, and a widget package must not replace a decoder the app chose. README and quick start show the line.

**Scope.** Kitty graphics only (the only protocol libghostty-vt 1.0 stores). Images are not selectable, not copied, and not in the semantics tree. The xterm adapter shows them too, since it builds a `VtTerminalView`; xterm 4.0.0 never drew images, so this is an addition, not a behaviour change of an existing member.

## Consequences
- `kitten icat`, `timg`, yazi previews and similar tools work once the app installs the PNG decoder (raw RGB/RGBA transmissions work without it).
- New public API: `decodeVtPng` and `VtTerminalController(imageStorageLimit:)`. No change to existing members.
- Test coverage: decoder conformance against PngSuite-style fixtures generated in tests plus random-byte and mutation fuzzing; widget tests that transmit images through the controller and check placement geometry, layer order, texture lifetime and animation ticking; a Linux golden.
